# Runbook: OpenShift Virtualization DR with AAP (PROD ⇄ DR)

Build the whole lab in one pass: **protect** a VM on PROD, **fail over** to DR, and **fail back** to PROD, all from AAP. Background and deeper detail: [REBUILD.md](REBUILD.md), [README](../README.md), and for failback [LAB-FAILBACK-EASY.md](https://github.com/mpmprock3/openshift-vm-dr-automation/blob/eb83b6d/docs/LAB-FAILBACK-EASY.md) / [FAILBACK-CONTINUATION.md](https://github.com/mpmprock3/openshift-vm-dr-automation/blob/eb83b6d/docs/FAILBACK-CONTINUATION.md).

> 📖 **How it works:** [Every AAP job in this runbook: which playbook it runs, where it redirects, and what it changes →](RUNBOOK-PLAYBOOK-FLOW.md)

The two clusters are **PROD** (where VMs normally run) and **DR** (the recovery site). They match your kubeconfig contexts:

```bash
oc config use-context PROD
oc config use-context DR
```

> **Four rules**
>
> 1. Every `oc` command uses `--context=PROD` or `--context=DR` (case-sensitive), so nothing runs on the wrong cluster.
> 2. Run commands from the repository root (step 1).
> 3. Never put tokens, passwords, kubeconfigs or the AAP manifest in Git, chat or job variables.
> 4. Each step ends with a ✅ **Checkpoint**. Don't move on until it passes.

## 0. What you build

```text
PROD cluster                                   DR cluster
 ├─ OpenShift Virtualization                    ├─ OpenShift Virtualization
 ├─ Trident + Trident Protect 26.02             ├─ Trident + Trident Protect 26.02
 ├─ AppVault trident-protect/lab-vault          ├─ AppVault trident-protect/lab-vault (same bucket)
 ├─ SA aap-automation/aap-dr-automation         ├─ SA aap-automation/aap-dr-automation
 ├─ Source VM default/dr-demo-vm                ├─ AAP 2.6 (namespace aap)  ← runs every job
 └─ VM prod-return-<id>/dr-demo-vm              └─ Recovered VM vmdr/dr-demo-vm (after failover)
    (after failback)
```

Three AAP workflows, used in this order:

| Workflow | What it does | How you get it |
|---|---|---|
| **Enable DR Protection** | Starts replicating the chosen VM from PROD to DR every 5 min | Built by hand (step 9) |
| **Fail Over to DR** | Stops the PROD VM and starts it on DR from the latest replica | Generated by a setup job (step 11) |
| **Fail Back to DC** | Copies DR changes back, stops DR with a final snapshot, starts the VM on PROD from that exact snapshot (new namespace `prod-return-<id>`), and turns protection PROD → DR back on | Generated by a setup job (step 13) |

> "DC" in AAP names (`Configure DC Protection`, `Fail Back to DC`) means **PROD**. Those names are hard-coded in the playbooks, so keep them exactly.

**Lab status.** Protection and failover have worked on live clusters. Failback (PR #2, commit `c4cbb49`) passes automated API-fixture tests but isn't merged yet, so step 13 is its first live run.

## 12. Fail over to DR

See [the failover field explanations and decision tables](SURVEY-GUIDE-AND-TESTS.md#4-fail-over-to-dr-fields) before launching. Source isolation mode controls whether Ansible stops PROD; fencing confirmation does not override that mode. This workflow requires acceptance of the existing replica and does not perform a final sync.

Wait at least one 5-minute interval after step 7's marker, then launch **Fail Over to DR**:

| Question | Answer |
|---|---|
| Protected VM group | `vmdr/demo-vm-plan-<hash>-mirror` |
| Failover request ID | `poc-failover-001` (reuse the same ID on retry) |
| How will the source be isolated? | `Stop source VMs` |
| Accept recovery without a final source sync? | `Yes` |
| Max replicated snapshot age | `15` |
| External fencing completed? | `No` |
| Health URL | *(empty)* |

It stops the PROD VM, promotes the DR replica and starts the VM on DR. Writes after the last replicated snapshot are lost, because this is a disaster failover. If a stage fails, fix the cause and relaunch the **whole** workflow with the **same request ID**.

✅ **Checkpoint**

```bash

oc --context=DR get appmirrorrelationships.protect.trident.netapp.io -n vmdr
oc --context=DR get vm,vmi,pvc -n vmdr
```

- PROD VM `Stopped`, no VMI. DR AMR `Promoted`. DR VMI `Running`.
- In the DR guest (`oc config use-context DR`, then `virtctl console dr-demo-vm -n vmdr`), `/root/1-written-on-prod.txt` exists.

Leave the VM running on DR. You'll write a DR-side proof file just before failback (step 13.4).

## 13. Fail back to PROD (≈20 min setup once, then one workflow)

**Fail Back to DC** continues from the failover you did in step 12. You pick the VM group in a survey; Ansible does the rest. When it finishes:

- `dr-demo-vm` runs on PROD in a **new namespace** `prod-return-<id>`.
- The old stopped `default/dr-demo-vm` and its disk are retained. **Keep it stopped.**
- PROD → DR replication is restored, and the catalog is updated so **Fail Over to DR** works again for the next cycle.

The key data-preservation step is stage 5: PROD recovers from DR's **final ShutdownSnapshot**, not an older scheduled snapshot. If the final snapshot fails, promotion is blocked.

All failback work runs through AAP. The few `oc` commands below only check the result.

### 13.5 Launch Fail Back to DC (downtime inside the workflow)

This stops the DR VM during the move. Both clusters must be reachable, and the original PROD copy must stay stopped.

1. Launch **Refresh Failback Groups** and wait for **Successful**.
2. Open a **new** **Fail Back to DC** launch form:

   | Survey question | Answer |
   |---|---|
   | Which protected VM group should return to DC? | `demo-vm-plan (default/dr-demo-vm) \| vmdr/demo-vm-plan-<hash>-mirror` |
   | Where should the VM return on PROD? | Keep **Dedicated PROD namespace (retain old copy)** |
   | Optional DC application health URL (HTTP 200 expected) | *(empty for this VM-only test)* |

3. **Launch** and watch until **Successful**. There's no fixed wait; the time depends on the copy and the boot.

The seven stages run automatically:

| # | Stage | What it does | VM runs on |
|---|---|---|---|
| 1 | Begin Failback | Reads the group from your failover catalog. Finds the actual DR VM and disks, adds stable protection labels, takes a baseline snapshot | DR |
| 2 | Prepare Failback DC | Confirms the old PROD VM is stopped, checks the destination namespace, removes the old PROD Application's managed snapshot schedules | DR |
| 3 | Release Failback DR | Deletes the old promoted relationship so DR can become the replication source. VM, disks and Applications stay | DR |
| 4 | Check Failback DC | Starts DR → PROD replication, waits for a successful transfer, checks PROD disks and that PROD can run VMs | DR |
| 5 | Shutdown Failback DR | Disables DR schedules, takes the **final ShutdownSnapshot**, checks it completed and covers every disk, confirms the DR VM is stopped | **downtime starts** |
| 6 | Recover Failback DC | Promotes **that exact snapshot** on PROD, checks the VM and disks, runs the optional health check | PROD |
| 7 | Reprotect Failback DR | Restores PROD → DR replication, waits for a successful transfer, updates the catalog for the next **Fail Over to DR** | PROD |

The workflow reports success only after both recovery and reprotection pass.

**Don't** edit Applications, mirrors or disks by hand, and don't run a manual enrollment job. If the dropdown has no eligible group, don't pick another VM as a workaround. Check that step 12 completed and the DR mirror is `Promoted`.

**Check the data.** In the **PROD console**, open `dr-demo-vm` in the **new** namespace (or run `oc config use-context PROD`, then `virtctl console dr-demo-vm -n prod-return-<id>`). Log in as the same guest user you used on DR:

```bash

```

```bash
  jsonpath='{range .items[*]}{.metadata.name} {.status.state} LastTransferSucceeded={.status.conditions[?(@.type=="LastTransferSucceeded")].status} last={.status.lastTransfer.completionTimestamp}{"\n"}{end}'
```

✅ `fb-app-<id>-mirror Established LastTransferSucceeded=True`. Run it again after 5+ minutes; `last=` must advance.

The guest IP can change on PROD. Check how clients reach the VM.

### 13.7 If a job fails

- Keep the original PROD copy stopped. Copy the failed task name and its error from AAP.
- **Don't** delete snapshots, ConfigMaps, PVCs or AMRs. They're the retry record.
- After fixing the cause, relaunch the **whole Fail Back to DC workflow** with the **same group** and the **same code revision**. Run **Refresh Failback Groups** first if needed; it also lists interrupted operations.
- **Never** do any of these:
  - launch the stage jobs on their own
  - start another failover while a failback is incomplete
  - set an AMR from `Promoted` to `Established` (that throws away DR changes)
  - cancel AAP and assume storage stopped too; NetApp controllers may still be reconciling

---

## 14. Repeat the cycle

After a successful failback the catalog points at the new PROD namespace, so you can go round again:

1. **Refresh Recovery Choices → Fail Over to DR** (step 12). Select the updated group and use a **new** request ID such as `poc-failover-002`. The source is now `prod-return-<id>`.
2. **Refresh Failback Groups → Fail Back to DC** (step 13.5).

You don't repeat setup or enrollment, and later returns reuse `prod-return-<id>`. **Never start the old `default/dr-demo-vm`.** When PR #2 is merged, set the project back to `main` and sync. Do this only between cycles, never during a failback.

## 15. Troubleshooting

| Symptom | Fix |
|---|---|
| VM "not found", wrong cluster | Always use `--context=PROD` / `--context=DR` |
| `bootstrap/automation-token-secret.yml` not found | Clone the `docs/one-pass-runbook` branch, run from repo root |
| AAP asks for a subscription | Upload a manifest (step 4.4) |
| `ClusterScopedResources access denied` | Apply `rbac_poc_cluster_admin.yml` on both clusters (step 5) |
| `HTTP 401 Unauthorized` mid-job | Token expired: use the non-expiring token (step 5) and update the credential |
| Survey errors (`Choose one or both supported protection scopes`, …) | Scope ticks must match the lists; namespace mapping must be **single** select |
| Workflow runs only 1 node | Save in the Visualizer, reopen, confirm 3 nodes |
| Dropdown shows old/no choices | Run the matching *Refresh …* job, then open a **new** launch form |
| `No eligible DR virtualization node` (failover) or a compute check fails at stage 4 (failback) | No KVM node: add `protect_allow_emulation: true` (step 6.3). For failback, also check **Fail Back to DC → Extra variables** (13.2), then relaunch |
| `Expected exactly one template named …` (setup jobs) | A base template is missing or misnamed; create it with the exact name from step 8 (failback setup needs **Configure DC Protection**, **Establish DR Replication** and **Refresh VM Choices**) |
| Failback setup reports a mismatched existing template | It names the exact setting; fix that field. Don't delete running jobs or reset journals |
| **Fail Back to DC** dropdown has no eligible group | Run **Refresh Failback Groups** and open a new form. Still empty: step 12 didn't complete, or the DR mirror isn't `Promoted` |
| Application stuck / `TMR … already exists` after a failed enrollment | Retry with a **new plan name and destination namespace**; never delete TMRs or finalizers |
| Wanted a 2-minute RPO | Not supported; 5 minutes is the minimum for this asynchronous design |
