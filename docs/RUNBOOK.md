# Runbook: OpenShift Virtualization DR with AAP (PROD ⇄ DR)

Build the whole lab in one pass: **protect** a VM on PROD, **fail over** to DR, and **fail back** to PROD, all from AAP. Background and deeper detail: [REBUILD.md](REBUILD.md), [FAILBACK.md](FAILBACK.md), [README](../README.md).

The two clusters are **PROD** (where VMs normally run) and **DR** (the recovery site). They match your kubeconfig contexts:

```bash
oc config use-context PROD
oc config use-context DR
```

> **Four rules**
>
> 1. Every `oc` command uses `--context=PROD` or `--context=DR` (case-sensitive), so nothing runs on the wrong cluster.
> 2. Run commands from the repository root (step 1).
> 3. Never put tokens, passwords, kubeconfigs or the AAP manifest in Git, chat or job variables.
> 4. Each step ends with a ✅ **Checkpoint**. Don't move on until it passes.

---

## 0. What you build

```text
PROD cluster                                   DR cluster
 ├─ OpenShift Virtualization                    ├─ OpenShift Virtualization
 ├─ Trident + Trident Protect 26.02             ├─ Trident + Trident Protect 26.02
 ├─ AppVault trident-protect/lab-vault          ├─ AppVault trident-protect/lab-vault (same bucket)
 ├─ SA aap-automation/aap-dr-automation         ├─ SA aap-automation/aap-dr-automation
 └─ Source VM default/dr-demo-vm                ├─ AAP 2.6 (namespace aap)  ← runs every job
                                                └─ Recovered VM vmdr/dr-demo-vm (after failover)
```

Three AAP workflows, used in this order:

| Workflow | What it does | How you get it |
|---|---|---|
| **Enable DR Protection** | Starts replicating the chosen VM from PROD to DR every 5 min | Built by hand (step 9) |
| **Fail Over to DR** | Stops the PROD VM and starts it on DR from the latest replica | Generated by a setup job (step 11) |
| **Fail Back to DC** | Copies DR changes back, stops DR, starts the VM on PROD with **no data loss**, and turns protection PROD → DR back on | Generated by a setup job (step 13) |

> "DC" in AAP names (`Configure DC Protection`, `Fail Back to DC`) means **PROD**. Those names are hard-coded in the playbooks, so keep them exactly.

**Lab status.** Protection and failover have worked on live clusters. Failback is implemented and tested in simulation only, so step 13 is its first live run.

## 1. Get the code and check contexts (≈5 min)

```bash

cd openshift-vm-dr-automation
oc config get-contexts PROD DR
oc --context=PROD whoami --show-server
```

✅ Both contexts exist, both logins work, and the two API URLs are **different**.

If a login expired, log in again and re-create the context:

```bash

oc config delete-context PROD
oc config rename-context "$(oc config current-context)" PROD
```

(Use `DR` instead of `PROD` for the DR cluster. Get the token from the console → your name → **Copy login command**.)

## 2. Check both clusters (≈10 min)

```bash
for c in PROD DR; do
  echo "===== $c ====="
  oc --context=$c get clusterversion
  oc --context=$c get csv -n openshift-cnv
  oc --context=$c get storageclass,volumesnapshotclass
  oc --context=$c get appvaults.protect.trident.netapp.io -n trident-protect
  oc --context=$c get deploy -n trident-protect -o custom-columns='NAME:.metadata.name,IMAGE:.spec.template.spec.containers[*].image'
  oc --context=$c get nodes -o custom-columns='NAME:.metadata.name,READY:.status.conditions[?(@.type=="Ready")].status,SCHEDULABLE:.metadata.labels.kubevirt\.io/schedulable,KVM:.status.allocatable.devices\.kubevirt\.io/kvm'
  oc --context=$c get kubevirt.kubevirt.io -n openshift-cnv -o jsonpath='{range .items[*]}useEmulation={.spec.configuration.developerConfiguration.useEmulation}{"\n"}{end}'
done
oc --context=DR adm top nodes
```

✅ **Checkpoint**, on **both** clusters:

- OpenShift Virtualization CSV is `Succeeded`.
- `storage-class-iscsi` (Trident) and `csi-trident-vsc` exist. `gp3-csi` stays the default class (AAP's database uses it).
- `lab-vault` is `Available` and points to the same bucket on both clusters.
- Trident Protect controller image is `netapp/controller:26.02.0`.
- **VMs can run there.** Either a node shows `KVM` > 0, **or** (POC labs) `useEmulation=true` and a node shows `READY=True` and `SCHEDULABLE=true`. Failover checks DR, failback checks PROD. With emulation you'll also set `protect_allow_emulation: true` in step 6.3.
- DR has free memory for AAP (~6–8 GiB) **plus** the recovered VM.

Missing Trident, Trident Protect or the AppVault? See [REBUILD.md §4](REBUILD.md#4-rebuild-netapp-prerequisites-on-both-clusters). ONTAP/SVM peering must already exist.

## 6. AAP base objects (≈15 min)

Everything goes in the same **Organization** (e.g. `Default`), under **Automation Execution → Infrastructure**.

### 6.1 Cluster credentials

**Credentials → Create**, type **OpenShift or Kubernetes API Bearer Token**, *Verify SSL* on:

| Name | API endpoint | Token |
|---|---|---|
| `OpenShift PROD` | `oc --context=PROD whoami --show-server` | PROD token |
| `OpenShift DR` | `oc --context=DR whoami --show-server` | DR token |

### 6.2 AAP API credential

The setup and refresh jobs use it to build workflows and fill survey dropdowns.

1. **Access Management → Users → `admin` → Tokens → Create token**, scope **Write**. Copy it.
2. **Credential Types → Create** `AAP Survey API`: paste `aap_survey_credential_inputs.yml` into *Input configuration* and `aap_survey_credential_injectors.yml` into *Injector configuration* (`cat` them from the repo).
3. **Credentials → Create** `AAP Survey Updater`, type `AAP Survey API`. *AAP base URL* is the gateway URL with **no path** (e.g. `https://aap-aap.apps.<dr-domain>`). *Token* is the token from step 1.

### 6.3 Inventory

**Inventories → Create** `DR-Automation` → **Hosts** → add `localhost` with:

```yaml
ansible_connection: local
ansible_python_interpreter: "{{ ansible_playbook_python }}"
protect_allow_emulation: true
```

Keep `protect_allow_emulation: true` only if your clusters use software emulation (step 2). It lets failover and failback accept a node with KVM = 0. If a node has real KVM, hardware is used anyway.

### 6.4 Project

**Projects → Create** `VMDR automation`: Git, URL `https://github.com/mpmprock3/openshift-vm-dr-automation.git`, branch **`main`**, no source-control credential (public repo).

✅ Project sync shows **Successful**. Re-sync whenever the code changes.

## 12. Fail over to DR

See [the failover field explanations and decision tables](SURVEY-GUIDE-AND-TESTS.md#4-fail-over-to-dr-fields) before launching. Source isolation mode controls whether Ansible stops PROD; fencing confirmation does not override that mode. This workflow requires acceptance of the existing replica and does not perform a final sync.

Wait at least one 5-minute interval after step 7's marker, then launch **Fail Over to DR**:

| Question | Answer |
|---|---|
| Protected VM group | `vmdr/demo-vm-plan-<hash>-mirror` |
| Failover request ID | `poc-failover-001` (reuse the same ID on retry) |
| How will the source be isolated? | `Stop source VMs` |
| Accept recovery without a final source sync? | `Yes` |
| Max replicated snapshot age | `15` |
| External fencing completed? | `No` |
| Health URL | *(empty)* |

It stops the PROD VM, promotes the DR replica and starts the VM on DR. Writes after the last replicated snapshot are lost, because this is a disaster failover. If a stage fails, fix the cause and relaunch the **whole** workflow with the **same request ID**.

✅ **Checkpoint**

```bash
oc --context=PROD get vm,vmi -n default
oc --context=DR get appmirrorrelationships.protect.trident.netapp.io -n vmdr
oc --context=DR get vm,vmi,pvc -n vmdr
```

- PROD VM `Stopped`, no VMI. DR AMR `Promoted`. DR VMI `Running`.
- In the DR guest (`oc config use-context DR`, then `virtctl console dr-demo-vm -n vmdr`), `/root/1-written-on-prod.txt` exists.

Now simulate work done on DR, which failback must bring home:

```bash
date | sudo tee /root/2-written-on-dr.txt; sync
```

## 13. Fail back to PROD (⚠ first live run)

**Fail Back to DC** returns the VM to PROD **without losing DR changes**, then protects it to DR again. You choose the group; everything else is automatic.

### 13.1 One-time setup (≈5 min)

1. Sync the project (failback code is on `main`).
2. Create two Job Templates (same inventory, project and EE; concurrent jobs off):

   | Name (exact) | Playbook | Credentials |
   |---|---|---|
   | `Refresh Failback Choices` | `refresh_failback_choices.yml` | OpenShift DR + AAP Survey Updater |
   | `Configure Failback Workflow` | `configure_failback_workflow.yml` | OpenShift DR + AAP Survey Updater |

   `Refresh Failback Choices` only serves as a settings template for the setup job; you don't need to launch it.
3. Launch **`Configure Failback Workflow`**. It creates the workflow **Fail Back to DC**, its seven stage jobs and **Refresh Failback Groups**. It doesn't stop or move anything.

✅ **Templates** now shows **Fail Back to DC**. If you use emulation, open it and check its **Extra variables** show `protect_allow_emulation: true`. It copies the inventory value; if it shows `false`, edit it to `true`.

### 13.2 Run it

1. Launch **`Refresh Failback Groups`**. It lists groups currently active on DR.
2. Open a **new** **Fail Back to DC** launch form:

   | Question | Answer |
   |---|---|
   | Which protected VM group should return to DC? | `demo-vm-plan (default/dr-demo-vm) \| vmdr/demo-vm-plan-<hash>-mirror` |
   | Optional DC application health URL | *(empty, or an HTTP URL that should return 200 from PROD)* |

3. Launch and watch the stages. Allow 30–60 min; the first copy back to PROD can be a full copy.

| # | Stage | Cluster | What happens | DR VM | PROD VM |
|---|---|---|---|---|---|
| 1 | Begin Failback | DR | Validates the group, takes a baseline snapshot | running | stopped |
| 2 | Prepare Failback DC | PROD | Checks PROD VM is stopped, removes the old PROD schedule | running | stopped |
| 3 | Release Failback DR | DR | Ends the old PROD→DR relationship, starts DR snapshots | running | stopped |
| 4 | Check Failback DC | PROD | Starts replication DR → PROD and waits for a good copy; checks PROD can run VMs | running | stopped |
| 5 | Shutdown Failback DR | DR | **Stops the DR VM** and takes a final snapshot (no more writes) | **stopped** | stopped |
| 6 | Recover Failback DC | PROD | Promotes PROD at that exact final snapshot and **starts the PROD VM** | stopped | **running** |
| 7 | Reprotect Failback DR | DR | Re-creates PROD → DR replication and updates the recovery catalog | stopped | running |

Downtime runs from stage 5 to stage 6. A failure in stages 1–4 leaves DR running. A failed final snapshot in stage 5 blocks stage 6, so PROD is never started from incomplete data.

### 13.3 Check the result

The last job reports `DC VM recovery verified and DC-to-DR replication Established`. Then:

```bash
oc --context=PROD get vm,vmi -n default
oc --context=DR get vm,vmi -n vmdr
oc --context=DR get appmirrorrelationships.protect.trident.netapp.io -n vmdr
oc --context=PROD get schedules.protect.trident.netapp.io -n default
```

✅ **Checkpoint**

| Check | Pass when |
|---|---|
| One active site | PROD VMI `Running`; DR has no VMI |
| No data lost | In the PROD guest (`oc config use-context PROD`, then `virtctl console dr-demo-vm -n default`), **both** `/root/1-written-on-prod.txt` and `/root/2-written-on-dr.txt` exist |
| Protected again | DR AMR `demo-vm-plan-<hash>-mirror` is `Established`; PROD has a schedule |
| Timing | Note stage 5 start → stage 6 end (planned downtime) |

### 13.4 If a stage fails

- Read the failed job's message, fix the cause, sync the project, and **relaunch the whole Fail Back to DC workflow with the same group**. It resumes from where it stopped.
- **Never** launch the stage jobs on their own, and don't run another DR workflow at the same time.
- **Never** delete the `reverse-…` / `cutover-…` ConfigMaps or `…-fb-…` snapshots. They're the retry record.
- **Never** "fail back" by setting an AMR from `Promoted` to `Established`. That throws away DR changes.
- Keep the stopped copy stopped: no manual starts, no GitOps restarts.

---

## 14. Repeat the cycle

After a successful failback the recovery catalog is updated, so you can go round again with the same VM:

1. Launch **Refresh Recovery Choices** → **Fail Over to DR** (step 12, with a **new** request ID such as `poc-failover-002`).
2. Launch **Refresh Failback Groups** → **Fail Back to DC** (step 13.2).

A new failback cycle is only accepted once the previous one completed.

## 15. Troubleshooting

| Symptom | Fix |
|---|---|
| VM "not found", wrong cluster | Always use `--context=PROD` / `--context=DR` |
| `bootstrap/automation-token-secret.yml` not found | Clone the `docs/one-pass-runbook` branch, run from repo root |
| AAP asks for a subscription | Upload a manifest (step 4.4) |
| `ClusterScopedResources access denied` | Apply `rbac_poc_cluster_admin.yml` on both clusters (step 5) |
| `HTTP 401 Unauthorized` mid-job | Token expired: use the non-expiring token (step 5) and update the credential |
| Survey errors (`Choose one or both supported protection scopes`, …) | Scope ticks must match the lists; namespace mapping must be **single** select |
| Workflow runs only 1 node | Save in the Visualizer, reopen, confirm 3 nodes |
| Dropdown shows old/no choices | Run the matching *Refresh …* job, then open a **new** launch form |
| `No eligible DR virtualization node` (failover) or same at stage 4 (failback) | No KVM node: add `protect_allow_emulation: true` (step 6.3), check the workflow variables (13.1), relaunch |
| `Expected exactly one template named …` (setup jobs) | A base template is missing or misnamed; create it with the exact name from steps 8 / 13.1 |
| Application stuck / `TMR … already exists` after a failed enrollment | Retry with a **new plan name and destination namespace**; never delete TMRs or finalizers |
| Wanted a 2-minute RPO | Not supported; 5 minutes is the minimum for this asynchronous design |

Diagnostics:

```bash
oc --context=PROD logs -n trident-protect deploy/trident-protect-controller-manager --since=30m | tail -100
oc --context=DR logs -n trident-protect deploy/trident-protect-controller-manager --since=30m | tail -100
oc --context=PROD get appmirrorrelationships.protect.trident.netapp.io -A
oc --context=DR get appmirrorrelationships.protect.trident.netapp.io -A
oc --context=DR get shutdownsnapshots.protect.trident.netapp.io -n vmdr
oc --context=DR get events -n vmdr --sort-by=.metadata.creationTimestamp
oc --context=PROD get events -n default --sort-by=.metadata.creationTimestamp
```

For step-by-step failback diagnosis (baseline only, reverse replication only), see [FAILBACK.md](FAILBACK.md).
